# تطوير قاعدة البيانات والحماية — المرحلة الأولى

الحالة: فرع مراجعة مستقل؛ لم يتم تشغيل SQL على Supabase. لا يتغير التطبيق المنشور أو سجلاته.

## البنية الحالية (حسب ملفات المشروع)
- Supabase/PostgreSQL، جدول مركزي للمالك وجدول شخصي منفصل. تخزين لقطة JSONB كاملة (حتى 2 MiB).
- الحفظ باستخدام RPC ومراجعة رقم الإصدار؛ مشاركة الموظفين بصلاحيات محددة؛ أرشيف مركزي لآخر خمس نسخ إذا فُعّل V9.3.
- الواجهة الحالية لا تتغير. الحساب المحلي دون تسجيل لا يكتسب صلاحية للوصول إلى قاعدة مركزية.

## ما يضيفه هذا الفرع
- مخطط خاص portfleet_v2 لا يتيح الوصول المباشر لـ anon/authenticated؛ RLS مفعّل لكل الجداول.
- جدول مساحات العمل؛ جدول سجل منفصل لكل عنصر مع مفتاح مركب وفهرس للترتيب؛ جدول روابط بمفاتيح أجنبية ضمن المساحة؛ جدول أحداث مراجعات يكتب من الخادم مع وقت ومعرّف منفذ العملية إن توفر وعدد السجلات المتغيرة.
- تحقق من بنية اللقطة، تكرار المعرّف، المراجع غير الموجودة، وحركة رقم المراجعة.
- مزامنة إسقاط السجلات مع اللقطة داخل المعاملة نفسها لجميع الكتابات بما فيها طلبات الموظفين. اللقطة تظل المصدر المعتمد. هذه مرحلة انتقالية وليست تحويل الحقول كلها إلى أعمدة وأنواع SQL مستقلة.
- لا تفعيل تلقائي للمصادقة الثنائية ولا تشفير جديد للتخزين المحلي ولا توسيع لصلاحيات الموظفين. سجل المراجعات ليس غير قابل للعبث من مسؤول قاعدة البيانات.

## قبل التطبيق
1. خذ نسخة احتياطية من قاعدة مشروع آليات المرفأ المخصص واختبر الاستعادة.
2. استخدم قاعدة اختبار مستقلة وطبّق ملفات الإعداد الحالية اللازمة (V8.1 وV9.3). لا تستخدم مشروع سوق الأسماك.
3. نفّذ migration ثم tests. يجب أن يساوي mismatched_records_expected_zero صفراً. عالج المراجع القديمة المفقودة بإجراءات مصرح بها؛ لا تحذفها تلقائياً.
4. اختبر على حسابين شخصيين ومالك وموظف: رفض الوصول المتقاطع والمستخدم غير الموثق، رفض الحفظ المتعارض، الطلبات المشتركة، انقطاع الشبكة، التزامن، النسخ والاستعادة. اختبار مرور الموظفين يتطلب بيانات وأدوار فعلية في بيئة الاختبار؛ لم يُنفذ بعد.
5. راقب حجم الجداول وزمن الكتابة: المرحلة تضيف نسخة مفهرسة من السجلات وتعيد بناء روابطها عند الحفظ؛ لا ترفع الحد الحالي. حدد سياسة احتفاظ بسجل المراجعات قبل اعتماد الإنتاج.
6. بعد نجاح الاختبار ومراجعة الأذونات، طبّق SQL على المشروع الصحيح. إذا فشلت المعاملة، لا تتغير اللقطات.

## تراجع آمن
إذا لزم إلغاء التفعيل بعد تطبيقه، أوقف الكتابات أولاً في نافذة صيانة وخذ نسخة احتياطية من مخطط portfleet_v2 وسجل الأحداث. احذف triggers الأربعة pf_v2_central_sync / pf_v2_personal_sync / pf_v2_central_delete / pf_v2_personal_delete من الجداول المناظرة فقط، مع إبقاء مخطط الإسقاط محفوظاً لأغراض التحقيق. لا تحذف جداول اللقطات أو الأرشيف الحالي. إعادة التفعيل تحتاج إعادة مزامنة مدروسة؛ لا تعِد تشغيل migration كما هو.

## مراحل لاحقة
تحويل الأعمدة التشغيلية إلى جداول نوعية، RPC لكل عملية بدلاً من استبدال اللقطة، ضبط التفويض من الخادم، MFA للمالك بعد إعداد الاسترداد، جلسات آمنة، نسخ احتياطية مستقلة واختبارات التحميل والأمان. لا تنقل البيانات الفعلية إلى GitHub أو خدمات خارجية.

## الاختبارات الآلية
تم إعداد GitHub Actions في الفرع لتشغيل PostgreSQL 16 مؤقتاً، مع محاكاة auth.uid والأدوار وحسابات وهمية فقط، ثم تطبيق ملفات V8.1 وV9.3 والمرحلة الأولى واختبارات الصلاحيات وسلامة المزامنة. لا تستخدم الاختبارات أي بيانات أو أسرار من Supabase الفعلي. نجاح الاختبار في بيئة PostgreSQL لا يثبت أن إعدادات Supabase الفعلية أو المصادقة أو أداء الحمل مطابقة. راجع نتيجة كل تشغيل على GitHub Actions قبل الانتقال للإنتاج.

## المرحلة الثانية: مصادقة المالك الثنائية (اختبار فقط)
- أضيفت شاشة تسجيل عامل TOTP والتحقق منه في owner.html على فرع المراجعة. لا تُخزن رموز TOTP أو مفتاح الإعداد في سجل التطبيق، ويُمنع فتح الإدارة إذا لم يحمل رمز الجلسة AAL2. تبقى استعادة الجلسة المحفوظة ممكنة فقط إذا كانت AAL2. تُرفض الجلسة عند فقد هذا المستوى بعد التجديد.
- 003_owner_mfa.sql يفرض AAL2 في سياسة القراءة المركزية ودوال الحفظ والأرشيف وإدارة الموظفين المعروفة في V8.1/V9.3. يبقى التحقق من هوية المالك متاحاً قبل التحدي. لا يُطبق على الحساب الشخصي أو موظف يملك صلاحية محددة، ولا على الوضع المحلي. راجع أي RPC إضافية موجودة على الخادم الفعلي.
- **لا تشغل 003_owner_mfa.sql على الإنتاج قبل تجربة الدخول الفعلي في مشروع اختبار منفصل، وتسجيل عامل المالك تحت إشرافه، واختبار عامل احتياطي/مسار الاسترداد لدى مسؤول Supabase.** تفعيل الإلزام مبكراً قد يقفل وصول المالك. لا تكشف مفتاح TOTP أو رمز التحقق لأي شخص. إذا ظهر عامل سابق غير مدعوم لا تتم إزالته آلياً؛ استخدم مسار الاسترداد المعتمد. التحقق الأولي يستخدم المفتاح اليدوي لا QR.
- اختبارات PostgreSQL تستبدل auth.jwt ببيانات وهمية للتحقق من التفويض فقط؛ اختبارات JavaScript تحاكي استجابات Auth. ليست اختباراً حقيقياً لرمز TOTP أو توقيع JWT أو واجهة الهاتف أو استعادة الحساب. لا يوجد ربط حي أو تغيير في قاعدة الإنتاج، ولا تشفير جديد للتخزين المحلي في هذه المرحلة.

## المرحلة الثالثة: الجلسات والخزنة المشفرة المحلية
- في owner.html (فرع المراجعة فقط): قفل الإدارة بعد عشر دقائق دون نشاط حقيقي من المستخدم، مع فحص المهلة عند استئناف الصفحة أو تجديد الجلسة أو إجراء طلب للخادم. إغلاق النماذج غير المحفوظة ومسح البيانات من واجهة وذاكرة التطبيق عند القفل باستخدام مسار القفل الموجود. لا يحذف القفل السجلات المحفوظة. يحاول إنهاء جلسة التجديد على الخادم؛ رمز الوصول الصادر قد يبقى صالحاً حتى انتهائه. لا يتم حفظ رمز تجديد جديد للمالك في localStorage؛ يُزال الرمز القديم المشترك فقط إذا تطابق مع هوية المالك المؤكدة عند الدخول. لا تغيير على تطبيق المستخدم الشخصي أو المحلي.
- local-vault.mjs: وحدة خزنة مستقلة تستخدم AES-256-GCM وPBKDF2-SHA256 بـ600000 دورة وملح عشوائي وIV عشوائي لكل كتابة، مع ربط المصادقة بمعرف المساحة ورقم الإصدار. تحفظ السجل والنسخة السابقة وبيانات المزامنة داخل غلاف واحد. تخزين IndexedDB بمعاملة مقارنة واستبدال لمنع تضارب التبويبات؛ لا يُخزن مفتاح التشفير أو عبارة المرور. لا يحمي من اختراق المتصفح أثناء فتح الخزنة أو استبدال الغلاف بنسخة قديمة صحيحة. فقد عبارة المرور قد يمنع استرجاع النسخة المحلية.
- **الخزنة ليست متصلة بعد بعمليات الحفظ والمزامنة في التطبيق.** بقيت البيانات المحلية الحالية كما هي؛ لا يدّعي هذا الفرع أنها مشفرة. يلزم تحويل الحفظ المتزامن إلى حفظ غير متزامن مع انتظار نجاح المعاملة قبل عرض النجاح، واختبار IndexedDB فعلياً على Chrome/Android، وتصدير نسخة مشفرة مستقلة والتحقق من فتحها، ثم ترحيل بيانات كل مساحة ومقارنتها قبل إزالة أي نسخة نصية قديمة. لا تخزن عبارة المرور في GitHub ولا تحذف localStorage يدوياً. ينبغي منع النسخ القديمة من إعادة الكتابة إلى المخزن القديم عند الترحيل.
- اختبارات Node تستخدم Web Crypto حقيقياً ومخزناً محاكياً، واختبارات المهلة تستخدم ساعة محاكاة؛ لا تغني عن اختبار الهاتف الفعلي أو اختبار Supabase الحي. مدة القفل عشر دقائق اختيار أولي قابل للمراجعة.
