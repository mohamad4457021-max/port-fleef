# Database V2 — مرحلة التأسيس

## الحالة
فرع تطوير مستقل، وليس ترقية مباشرة للإنتاج. قاعدة الإصدار الحالي تخزن جميع مجموعات السجلات في JSONB مع رقم مراجعة؛ الموظفون ومساحات الحسابات الشخصية مرتبطون بواجهات RPC الحالية. لم تتغير واجهات RPC أو تطبيقات الهاتف.

## المرحلة المنفذة
- `001-shadow-schema.sql`: مخطط خاص باسم portfleet_v2، 12 جدول سجلات وجدول workspace. لكل سجل مفتاح مرتبط بمالك المساحة ومعرّف السجل القديم، وموضعه في المصفوفة الأصلية، وحقول ذات أنواع محددة، ونسخة JSONB أصلية لحفظ الحقول الأخرى دون إسقاطها.
- مفاتيح خارجية تمنع الربط بسجل في مساحة مالك آخر، وفهارس لاستعلامات الآليات والصيانة والوقود والمستودع وغيرها. قيد تفرد للأكواد مع توحيد الأرقام العربية والفارسية والمسافات وحالة الأحرف؛ مطابقة NFKC مع المتصفح لم تستكمل.
- فحص أرصدة الوقود التاريخية على مستوى اليوم أثناء الاستيراد؛ القيد ليس بعد محركاً للعمليات المالية المتزامنة.
- استيراد ذري لنسخة مالك واحدة عند مراجعة محددة، مع مطابقة جميع المصفوفات وترتيبها ومحتواها الأصلي، ورفض إعادة الاستيراد فوق نسخة مرحّلة.
- منع وصول anon و authenticated إلى المخطط الجديد. لا تضفه إلى Supabase exposed schemas. الوظائف بصلاحية المستدعي وليست SECURITY DEFINER.
- `002-smoke-test.sql`: اختبار أولي للترحيل والعزل والصلاحيات والمطابقة، يجري داخل معاملة تنتهي بـ rollback. يتطلب نسخة تجريبية موجودة في قاعدة المصدر.

## طريقة الاختبار
1. جهّز مشروع PostgreSQL/Supabase منفصلاً للاختبار مع المخطط V1 ومالك تجريبي وبيانات صناعية. لا تستخدم قاعدة سوق الأسماك أو قاعدة المرفأ الفعلية.
2. شغّل 001 مرة واحدة بصلاحية مسؤول قاعدة البيانات. إذا فشل التنفيذ تُلغى المعاملة؛ لا تشغل الملف مرة ثانية على مخطط موجود دون مراجعة.
3. شغّل 002 في المشروع التجريبي. يجب أن يظهر PASS ولا تبقى بيانات مستوردة نتيجة الاختبار.
4. جرّب بيانات تالفة عمداً: معرفات مكررة، مراجع مفقودة، رصيد وقود سالب، حالات غير صحيحة. يجب أن يرفض الاستيراد بالكامل؛ لا تحذف السجلات الأصلية لمعالجة الرفض.
5. في اختبار لاحق وبعد نسخة احتياطية مستقلة، استخدم stage_owner مع UUID المالك ورقم المراجعة المعروف، ثم verify_owner. نجاح المطابقة لا يعني أن النسخة ستبقى متزامنة؛ أي تغير في مراجعة المصدر يجعل verify_owner يرفض المقارنة.

## ما لم ينفذ بعد
- نجحت اختبارات PostgreSQL 16 على بيانات اصطناعية في CI؛ لم تُجر اختبارات Supabase الحية أو اعتماد مؤسسي.
- هذا المخطط نسخة مرحلية للمالك فقط؛ لم يرحل حسابات الموظفين أو الحسابات الشخصية ولم يضف API كتابة/قراءة للبرنامج.
- الحقول المكتوبة في الأعمدة والعناصر الأصلية محفوظة معاً؛ قبل تفعيل الكتابة يجب اعتماد مصدر حقيقة واحد ومنع التباين بينهما. سجلات التدقيق المستوردة ليست سجل تدقيق مؤسسياً غير قابل للتعديل.
- عولج التزامن في النموذج الخاص للمحروقات والمستودع فقط؛ لم يكتمل لجميع العمليات أو تكامل التطبيق. ستضاف معاملات الخادم، سجل تدقيق من الخادم، صلاحيات تفصيلية، وسياسة نقل تدريجي قابلة للتراجع بعد اختبار الترحيل.
- لا تعديل على واجهات الإصدار الحالي ولا تغيير تلقائي في بيانات المستخدم.


## المرحلة التالية: محرك المعاملات (نموذج خاص)
- 003: فحص مسبق للمعرفات والأكواد والمراجع والأرقام دون تعديل المصدر. 004: حالات اختبار صناعية.
- 005: سجل إضافي مستقل لحركات الوقود مع قفل مساحة المالك، تحقق من مراجعة المصدر، رقم تسلسلي للمعاملة ومعرف عملية لمنع التكرار عند إعادة المحاولة، وسعة الخزان والرصيد التراكمي اليومي. لا يعدل نسخة V1 أو صفوف الترحيل الأساسية. يسجل هوية جلسة قاعدة البيانات وليس هوية الموظف؛ لا يمنح صلاحيات تنفيذ للمستخدمين.
- 006: اختبارات قبول ورفض وعودة المعاملة، لا تختبر جلسات متزامنة فعلية بعد. محرك الوقود تجريبي لا يحسب الاستهلاك الفعلي ولا يغير عداد الآلية، ولا يطبق الصرف من المستودع أو تكليف السيارات.
- CI: PostgreSQL 16 مؤقت وبيانات اصطناعية، بدون بيانات المرفأ أو مفاتيح Supabase. فشل التشغيل الأول عند تعريف غلاف دالة التشخيص بعد نجاح إنشاء الجداول واختبار الترحيل. صُحح خطأ محددات dollar quoting. نتائج التشغيل الأحدث تُراجع في Actions.
- لا تشغيل في قاعدة الإنتاج ولا ربط للواجهة قبل اجتياز اختبارات التزامن، صلاحيات المستخدم الفعلية، والتكامل مع المزامنة والنسخ الاحتياطي. لا تعرض المخطط الخاص في PostgREST.


## استكمال محرك المستودع والتزامن
- 007: محرك معاملات قطع الغيار الخاص. رصيد البداية هو كمية الصنف المرحّلة، وتضاف الحركات الجديدة فقط. يمنع الصرف فوق الرصيد ويربط الصرف بأمر عمل معتمد أو قيد الإصلاح وآلية متوافقة مع القطعة. يسجل التكلفة والرصيد بعد الحركة. يعتمد على قفل مساحة المالك ومراجعة المعاملة ومعرف فريد للعملية. لا يحدث رصيد الجدول الأساسي ولا واجهة V1، ولا يسمح بكتابة الموظفين بعد.
- 008: اختبارات القبول والرفض والاستعادة، وتحقق من عدم تغير مصدر الترحيل.
- ci-concurrency.py: اتصالات PostgreSQL مستقلة ومتوازية، تتحقق من تعارض الصرف، إعادة إرسال المعاملة نفسها، الرصيد وعدم قبول معاملات جديدة على نسخة مرحّلة قديمة. تعمل فقط في قاعدة CI الاصطناعية.
- ثبت نجاح تشغيل CI للمحرك السابق (الترحيل، الفحص، معاملات الوقود) في التشغيل 46176708494. لا تعد نتائج اختبار النسخة السابقة اعتماداً للمحرك الجديد.
- لا تُستخدم أو تُرحّل السجلات الحقيقية قبل توفير بيئة اختبار خاصة بالمرفأ وإثبات الصلاحيات والمزامنة والاستعادة على مستوى التطبيق.

## بوابات الاعتماد المؤسسي
1. CI ناجح للنسخة المعنية، بما في ذلك رفض تعارض عمليتين متزامنتين.
2. اختبار Supabase مع حساب مالك وموظف وحساب شخصي وغير مصرح له؛ لا يكفي دور postgres في CI.
3. إكمال واجهة API مع هوية المستخدم من الخادم، وصلاحيات تفصيلية وعمليات غير قابلة للتكرار، وسجل تدقيق مستقل. حل التباين بين payload والأعمدة قبل الكتابة.
4. تحديد مصدر حقيقة واحد وخطة انتقال مع تجميد الكتابة وقت النقل؛ اختبار ترحيل كل المساحات والتطابق والتراجع. لا تشغل محركي V1 وV2 على أرصدة تشغيلية واحدة دون بروتوكول انتقال.
5. اختبار استعادة نسخة احتياطية في قاعدة منفصلة مع قياس زمن الاستعادة وفقد البيانات المقبول وفق سياسة المرفأ.
6. اختبار المتصفح والهاتف والمزامنة دون اتصال وعند عودة الشبكة، واختبار الضغط وفق عدد مستخدمي المرفأ الحقيقي.
7. تشغيل تجريبي بالتوازي مع السجلات الرسمية، وتوثيق نتائج القبول واعتماد مسؤول النظام والمستخدمين المخولين.


## الصلاحيات والتدقيق — 009 / 010
- API تجريبي في مخطط منفصل portfleet_v2_api، لا تضفه إلى exposed schemas. يتطلب تفعيل مساحة اختبار من DBA، ويستخدم auth.uid() وهوية الحساب المؤكد. رفض افتراضي، منح مستقل لكل من fuel.post و inventory.post من المالك، وإلغاء فوري عند المعاملة التالية. لا يتم نقل صلاحيات V1 تلقائياً.
- قفل مساحة API ينسق تعديل الصلاحيات مع تسجيل الحركات. الحركات وحدث التدقيق ضمن معاملة واحدة. إعادة الطلب بنفس المعرف والبيانات والفاعل لا تضيف حركة أو حدثاً ثانياً. لا يُعتمد سجل كتبه DBA مباشرة دون حدث موثق.
- سجل رقابي بإضافة فقط، توقيت من الخادم ومعرف الفاعل، وعرض مجزأ للمالك. منع تعديل/حذف/تفريغ السجل على مستوى المشغل العادي؛ مسؤول قاعدة البيانات ذو الصلاحيات العليا يستطيع تغيير البنية، لذا ليس سجلاً غير قابل للتلاعب مطلقاً.
- 010: اختبارات SQL تحت دور authenticated وهويات اصطناعية متعددة؛ تشمل العزل بين مالكين، منع رفع الصلاحيات، إلغاء الوصول، منع تكرار التدقيق، الصفحات، وحجب الجداول الداخلية. محاكاة auth.uid في CI لا تختبر توقيع JWT أو PostgREST أو جلسات Supabase الحقيقية.
- ما زال التشغيل الفعلي محظوراً قبل ربط الواجهة، وإكمال مصدر الحقيقة، ومزامنة الصلاحيات مع النظام الحالي، واختبار الاستعادة. جميع نماذج V2 منفصلة عن النسخة العاملة.


## المزامنة والتخزين المحلي — 011 / 012 / client
- نجحت اختبارات 009/010 في تشغيل PostgreSQL CI رقم 46177515196 (هويات اصطناعية، لا JWT حقيقية).
- 011: واجهة حالة المزامنة لمجالي الوقود والمستودع، تعيد مراجعة المصدر وتسلسل المجال كنصوص لتفادي فقد دقة الأعداد الكبيرة، وإيصال عملية للفاعل نفسه فقط بعد التحقق من صلاحياته الحالية. ترفض الحالة عند تغير نسخة V1. لا توفر بعد تنزيل جميع السجلات أو دمج التعديلات.
- 012: اختبارات حالة المزامنة والإيصالات وعزل المستخدمين وإلغاء الصلاحيات.
- client/offline-outbox.mjs: طابور IndexedDB خاص بالنسخة التجريبية، مفصول حسب المالك والفاعل. يُحفظ الطلب قبل الإرسال مع معرف ثابت، ويُعاد إرساله عند انقطاع الاتصال دون تغيير معرّفه أو مراجعته. تأكيد محلي بعد إيصال الخادم. قفل مؤقت لكل محاولة عبر معاملة IndexedDB لمنع إرسال متكرر من تبويبين، واسترداد المحاولة بعد انتهاء القفل. تعارض المراجعة أو رفض الصلاحية يوقف الطابور في المجال المعني للمراجعة؛ لا دمج آلي ولا تجاوز للرصيد. العمليات غير المؤكدة ليست قيوداً تشغيلية معتمدة.
- client/offline-outbox.test.mjs: اختبارات Node مع fake-indexeddb@6.0.0 (للاختبار فقط)، ومحاكاة اتصال وAPI؛ ليست اختبار متصفح حقيقي أو Supabase. لا تخزن رموز الدخول في IndexedDB. التخزين المحلي غير مشفر وقد يحذفه النظام/المستخدم. يلزم جهاز موثوق وسياسة حماية بيانات ونسخ احتياطي واختبار التخزين الفعلي.
- لم يُربط هذا الطابور بواجهة V1، أو بمصادقة Supabase الحية. يجب بناء موصل transport مرتبط بجلسة ثابتة والتحقق منها قبل كل RPC وعدم إعادة استخدام جلسة مستخدم آخر. يلزم واجهة مراجعة العمليات الموقوفة، اختبار المتصفحات، واستراتيجية صريحة للترحيل والاستعادة قبل نشره. لا تعتبر هذه المرحلة مزامنة كاملة لقاعدة البيانات أو تصريحاً بالعمل المؤسسي دون اتصال.


## الاستعادة وربط واجهة المزامنة التجريبية
- نجح تشغيل 46177830249 لاختبارات حالة المزامنة وطابور IndexedDB (محاكي، لا هاتف فعلي).
- ci-backup-restore.py: اختبار آلي باستخدام pg_dump وpg_restore في قاعدة أخرى داخل عنقود PostgreSQL التجريبي نفسه. يتضمن بيانات اصطناعية من مصدر V1 وV2 والحركات والصلاحيات والتدقيق، ويقارن عدد ومحتوى الصفوف بواسطة SHA-256 وتسلسل سجل التدقيق. يختبر استمرار الصلاحيات وإعادة الطلب دون تكرار بعد الاستعادة، وكتابة عملية جديدة على القاعدة المستعادة فقط. يقيس حجم النسخة وزمن إنشائها واستعادتها. لا يصدر النسخة كملف عام ويحذف الملف المؤقت والقاعدة التجريبية. لا تستخدمه على بيانات حقيقية؛ لا يثبت الاستعادة على خادم آخر أو نسخ الأدوار أو استعادة Supabase أو RPO/RTO للمرفأ.
- staging-transport.mjs: موصل RPC تجريبي يربط الطلبات بهوية جلسة المستخدم ويتحقق منها قبل الطلب وبعده؛ يمنع إرسال معرف فاعل من العميل، ويقصر الاتصالات على HTTPS، ويرفض مفاتيح service_role المعروفة. مفاتيح المشروع العامة فقط. الاختبار يحاكي الشبكة وتبديل الحساب وتحديث الرمز. لا توجد مفاتيح فعلية أو نشر أو استدعاء لخدمة حية.
- لا يحقق الاختبار نسخاً احتياطياً مجدولاً للإنتاج أو تشفير ملفات النسخ على الخادم. يلزم اختيار سياسة النسخ المشفرة والاحتفاظ بها في مكان منفصل، وتحديد أهداف RPO/RTO واختبارها في بيئة مماثلة للمرفأ قبل الاعتماد.
- لا يزال مطلوباً استكمال معاملات الصيانة والتكليف والمناوبات، ربط الواجهة الفعلية، واختبار مزامنة جميع الأقسام والأداء والحماية والتعافي على بيئة Supabase مخصصة. لا تفعّل API التجريبية على قاعدة الإنتاج.
